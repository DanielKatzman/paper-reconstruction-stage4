# Runtime and asset setup

Use separate interpreters: Stage 1/2 were validated with Python 3.14.7; Stage 3 uses Python 3.12.10/Torch 2.7.1+cu118; Stage 4 uses Python 3.12.10. Stage 1/2 use ONNX Runtime; Stage 4 uses NumPy/SciPy/Pillow and the shared SDK. Existing component constraints are retained. `local/runtimes.json` maps `stage1`…`stage4` to interpreter paths and is ignored by Git. Every subprocess imports inlined source through an explicit `PYTHONPATH` that replaces inherited sibling-project paths.

`tools/setup.ps1` creates environments under ignored `local/envs` and installs editable components. It requires package-index access; it was not used to replace the already validated workstation environments during export. For a different OS or Python version, install the same four packages with the shared SDK in appropriate environments and supply the mapping. The packaging checks qualify the current Windows workstation, not every installation platform.

`provenance/assets.json` lists every optional model, benchmark input, saved evidence bundle, evaluation reference and original prediction by size and SHA-256. `tools/assets.py verify --groups models bundles inputs references` checks serving/evaluation assets. Original predictions are an optional additional group, never an initialization seed. Private source-page collections, training checkpoints/datasets, environments and historical output trees remain in the original projects.

`tools/package_assets.py` makes `models-v2.0.0.zip`, `benchmark-v2.0.0.zip` and checksums under ignored `local/release-assets`. The model archive contains the two ONNX networks and two small Torch rankers. Manifests are already in the source repository. Extract archives at the repository root; validate before running. They are intended as optional GitHub Release assets when publication is authorized. Source page redistribution rights should be preserved; the benchmark archive is local until explicitly uploaded.

The new `pipeline.py` requires a fresh output folder. On failure, logs and committed Stage 3 caches remain available for diagnosis; automatic inference continuation/resume is not implemented in this portable umbrella runner. If only post-seal evaluation needs to be repeated, use `python -B tools/pipeline.py evaluate --run outputs/<run>`; it authenticates the prediction barrier before opening references and preserves prediction files. Original Stage 3 and Stage 4 component CLIs retain their own validated resume policies. `--resume` on the historical experimental controllers is not a replacement for the portable commands.

The default development route requires an existing Stage 1 folder with `segmentation_manifest.jsonl` and a bound `capture_profile.json`. It reruns Stage 2/verification, Stage 3 native inference/pooling and Stage 4. The source Stage 1 generator is included at `stages/stage1/src/universal_segmenter/generation`; its original training data and source PDFs are optional private inputs. The exact benchmark inputs are preserved as assets, so regeneration is not required to reproduce the saved cohort.

For a capture folder, use `--captures`, `--mode shared-scale-capture` and an explicit `--capture-profile`. Stage 1 runs with its calibrated model and the selected review mode. The profile must truthfully declare native common scale, no per-piece resizing and no perspective. The pinned Stage 3 runtime refuses incompatible acquisition assumptions. The development-only exact-mask page profile must never be forged for real captures. The capture route uses the earlier general continuation solver and is not the qualified V21 thirty-piece baseline.

Generated result JSON includes status, selected layouts and complete diagnostics; a subprocess exit code of zero only means it published normally. A partial or unsupported layout is not a successful reconstruction. The benchmark review requires supported status, connectivity, no false selected neighbors, complete inventory and common-gauge measurements. Its explicit offline regression policy allows up to 48 native pixels maximum saved-probe displacement, relative orientation error at most 0.001 degrees and scale error at most 0.00001. This protects against a wrong/scaled/far-displaced piece hiding behind correct neighbor IDs; it does not change serving gates or certify unseen-page reliability. Four-pixel exactness remains a diagnostic. Preview review is still required.
